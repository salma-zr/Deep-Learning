\begin{abstract}
We ran a comparative study on medical question answering using the Medical Flashcards dataset. The experiments cover three settings: local closed-book generation, retrieval-augmented generation (RAG), and QLoRA fine-tuning on Google Colab with 1k/5k/20k training subsets. We kept the protocol practical and reproducible, then evaluated with ROUGE-L, BLEU, a local semantic judge (\texttt{flan-t5-large}), latency/format statistics, and qualitative review. In our runs, the best lexical results come from fine-tuning (\texttt{finetune\_5k}: ROUGE-L 0.2757, BLEU 0.1428), while the strongest non-fine-tuned setup is web RAG (\texttt{exp\_17}: ROUGE-L 0.1582). We also report where things fail, especially over-abstention under uncertainty prompting and the local judge tendency to cluster around partial scores.

\section{Introduction}

Medical QA looks straightforward at first, but in practice it is hard to keep both factual accuracy and usable answer format. Large language models make the task more accessible, but they also introduce obvious risks, especially hallucinations and overconfident errors.

This project explores various approaches to answering medical questions from a flashcard-style dataset, comparing:

\begin{itemize}
    \item \textbf{Closed-book generation}: LLMs answering from parametric knowledge
    \item \textbf{Prompt engineering}: Optimizing instructions for better outputs
    \item \textbf{Fine-tuning}: Domain adaptation with LoRA/QLoRA
    \item \textbf{Retrieval-Augmented Generation (RAG)}: Grounding responses in retrieved knowledge
\end{itemize}

Our objectives are:
\begin{enumerate}
    \item Compare performance across model sizes and providers
    \item Evaluate the impact of different prompting strategies
    \item Assess the benefits of fine-tuning on domain-specific data
    \item Analyze RAG for knowledge grounding and hallucination reduction
    \item Provide honest discussion of limitations and practical considerations
\end{enumerate}

\subsection{Project Framing and Brainstorming}

At the start, we had too many possible directions (cloud APIs, local models, several retrievers, full fine-tuning, many prompt variants). We narrowed this down into controlled comparisons so the final report would stay coherent and executable:
\begin{itemize}
    \item \textbf{Prompt axis}: same model, different prompts (strict, flashcard, uncertainty).
    \item \textbf{Retrieval axis}: same generator, different external sources (Wikipedia vs web) and different top\_k.
    \item \textbf{Evaluation axis}: combine automatic metrics, semantic judging, and manual qualitative checks.
\end{itemize}
This helped us avoid random trial-and-error and keep one consistent story from setup to evaluation.

\subsection{Research Questions and Success Criteria}

To keep the project focused, we turned the brainstorming list into three concrete research questions:
\begin{itemize}
    \item \textbf{RQ1 (Prompting):} With the same local model, how much can prompt design improve medical QA quality and output format?
    \item \textbf{RQ2 (Grounding):} Does RAG improve answer quality compared with closed-book generation, and under which retrieval settings?
    \item \textbf{RQ3 (Adaptation):} Does LoRA/QLoRA fine-tuning on domain data provide measurable gains over local non-fine-tuned baselines?
\end{itemize}

We treated an experiment as a real improvement only when gains were visible across at least three angles: lexical score, judge score, and qualitative plausibility.

\section{Methods}

\subsection{Closed-Book Generation}

In closed-book mode, the model answers directly with no retrieved context. So the output relies on what is already stored in model parameters.

\textbf{Models evaluated}:
\begin{itemize}
    \item OpenAI GPT-4o-mini (cloud API, cost-efficient)
    \item Llama 3.1 8B via Ollama (local inference)
    \item Mistral 7B via OpenRouter (free tier)
    \item Flan-T5-base (CPU fallback)
\end{itemize}

\subsection{Prompt Engineering}

We evaluate three prompting strategies:

\begin{enumerate}
    \item \textbf{One-sentence strict}: Explicitly requests single-sentence answers
    \begin{quote}
    \textit{``Answer the following medical question in exactly one clear, concise sentence.''}
    \end{quote}
    
    \item \textbf{Flashcard style}: Frames the task as flashcard completion
    \begin{quote}
    \textit{``Complete this medical flashcard with a brief, accurate answer.''}
    \end{quote}
    
    \item \textbf{Uncertainty allowed}: Permits ``Insufficient information'' responses
    \begin{quote}
    \textit{``If you are uncertain, respond with `Insufficient information.'\,''}
    \end{quote}
\end{enumerate}

\subsection{Fine-tuning with LoRA/QLoRA}

Parameter-efficient fine-tuning using Low-Rank Adaptation:

\begin{itemize}
    \item \textbf{Method}: QLoRA with 4-bit quantization
    \item \textbf{LoRA rank}: 16
    \item \textbf{LoRA alpha}: 32
    \item \textbf{Target model}: TinyLlama-1.1B-Chat
    \item \textbf{Training sizes}: 1k, 5k, 20k examples
\end{itemize}

This approach allows fine-tuning with limited GPU memory ($\sim$8GB VRAM).

\subsection{Retrieval-Augmented Generation (RAG)}

Combining retrieval with generation for knowledge grounding:

\begin{enumerate}
    \item \textbf{Retrieve}: Query Wikipedia for relevant medical content
    \item \textbf{Format}: Inject retrieved context into prompt
    \item \textbf{Generate}: LLM produces answer conditioned on context
\end{enumerate}

\textbf{Ablations}:
\begin{itemize}
    \item Number of retrieved documents (top\_k = 3 vs 5)
    \item Maximum context length
    \item Retriever type (Wikipedia vs Web)
\end{itemize}

\subsection{Fair Comparison Protocol}

To keep comparisons fair enough, we used a simple protocol:
\begin{itemize}
    \item same evaluation split per comparison block (mainly \texttt{tiny\_test}),
    \item deterministic decoding (temperature 0.0),
    \item one answer per question (no reranking),
    \item identical evaluation pipeline for every predictions file (\texttt{metrics + judge + qualitative}).
\end{itemize}
This does not remove all bias, but it avoids the most common comparison mistakes (different decoding settings or inconsistent post-processing across methods).

\section{Evaluation Methodology}

\subsection{Automatic Metrics}

\subsubsection{ROUGE-L}

Longest common subsequence F1 score between prediction and reference. Captures word-level overlap while respecting word order.

\textbf{Limitation}: Penalizes valid paraphrases and synonyms.

\subsubsection{BLEU}

N-gram precision with brevity penalty, computed using sacrebleu. Standard machine translation metric.

\textbf{Limitation}: Very strict for short-form QA; synonyms receive zero credit.

\subsection{LLM-as-a-Judge}

For this report, we used a local judge (\texttt{google/flan-t5-large}) for semantic scoring. We initially planned a cloud judge, but we prioritized a fully reproducible local pipeline:

\begin{itemize}
    \item \textbf{Score 2} (Correct): Semantically equivalent to reference
    \item \textbf{Score 1} (Partial): Some correct information, but incomplete
    \item \textbf{Score 0} (Wrong): Incorrect, irrelevant, or contradictory
\end{itemize}

\textbf{Consistency verification}: We re-judge a subset of examples to estimate judge reliability.

\subsection{Format Statistics}

Additional metrics for output quality:
\begin{itemize}
    \item Average answer length (characters, words)
    \item Multi-sentence percentage
    \item Empty response rate
    \item ``Insufficient information'' rate (for uncertainty prompts)
\end{itemize}

\subsection{Implementation Notes from the Project Process}

These are implementation points that directly affected validity of the results:
\begin{itemize}
    \item \textbf{Fine-tuning data-size bug fixed}: an early CLI path could silently use the full training file instead of the intended 1k/5k/20k subsets. We fixed this and enforced explicit dataset binding.

\end{itemize}

\subsection{Main Quantitative Observations}

\begin{enumerate}
    \item Fine-tuning is ahead on lexical metrics in our runs. The top ROUGE-L is \texttt{finetune\_5k} (0.2757), with \texttt{finetune\_20k} at 0.2714 and \texttt{finetune\_1k} at 0.2607. BLEU follows the same pattern overall (\texttt{finetune\_5k}: 0.1428, \texttt{finetune\_20k}: 0.1445, \texttt{finetune\_1k}: 0.1299).
    \item Scaling data helps, but not in a perfectly monotonic way on every metric. Going from 1k to 5k improves ROUGE-L and BLEU, while 20k gives the highest judge mean (1.24) with slightly lower ROUGE-L than 5k.
    \item Prompt engineering still matters even before fine-tuning. In closed-book local runs, flashcard prompting (\texttt{exp\_13}, ROUGE-L 0.1328) is stronger than strict one-sentence prompting (\texttt{exp\_12}, 0.1025) and simple direct prompting (\texttt{exp\_11}, 0.0855).
    \item RAG performance is very sensitive to retrieval setup. Web retrieval (\texttt{exp\_17}, ROUGE-L 0.1582) beats Wikipedia top-k=3 (\texttt{exp\_15}, 0.0866), while moving to top-k=5 (\texttt{exp\_16}, 0.0576) hurts both quality and latency.
    \item The latency/quality trade-off is clear in practice. Closed-book Flan-T5 runs are fast (roughly 120--265ms mean), RAG adds retrieval cost (roughly 925--1451ms mean), and fine-tuned TinyLlama on CPU is slowest at inference (roughly 6.3--6.7s mean) but gives the best overlap scores.
\end{enumerate}

\section{Qualitative Analysis}

We used the generated HTML reports plus manual inspection of representative examples from all families (closed-book, RAG, fine-tuned). The goal was to track recurring behavior, not to only show best-case outputs.

\subsection{Successful Cases}

\begin{itemize}
    \item Fine-tuned models (\texttt{finetune\_1k/5k/20k}) generally produce richer medical answers than non-fine-tuned local baselines, which matches the ROUGE-L/BLEU gap.
    \item \texttt{finetune\_20k} has the highest judge mean (1.24) and the highest correct rate in this report (24\%), even though lexical gain over \texttt{finetune\_5k} is small.
    \item In non-fine-tuned settings, web RAG (\texttt{exp\_17}) is the strongest lexical setup (ROUGE-L 0.1582), so retrieval source choice is clearly important.
    \item Flashcard prompting (\texttt{exp\_13}) improves both overlap and structure relative to simple direct prompting.
\end{itemize}

\subsection{Failure Cases}

\begin{itemize}
    \item The uncertainty-allowed prompt (\texttt{exp\_14}) collapsed into near-total abstention: 100\% ``Insufficient information'' and ROUGE-L 0.0004.
    \item Raising RAG context from top\_k=3 to top\_k=5 reduced quality (ROUGE-L 0.0866 \(\rightarrow\) 0.0576) and increased latency (925ms \(\rightarrow\) 1451ms), likely because of extra noise.
    \item Fine-tuned outputs are much longer (around 310 characters on average) and often multi-sentence. That helps content, but it can violate strict flashcard formatting.
    \item We still saw plausible but incorrect details across all families, mostly on multi-step or multi-entity questions.
\end{itemize}

\subsection{Controversial Cases}

Several experiments show metric-judge divergence:

\begin{itemize}
    \item \texttt{finetune\_5k} has the highest ROUGE-L (0.2757), but \texttt{finetune\_20k} gets the higher judge mean. So lexical and semantic rankings do not fully align.
    \item The uncertainty prompt has the weakest lexical metrics but still a near-partial judge mean (0.9875), which suggests the local judge may over-credit safe abstentions.
    \item Judge means stay close to score 1 in many runs, so we use judge output as support, not as final truth.
\end{itemize}

\section{Discussion}

\subsection{Key Findings}

\begin{enumerate}
    \item Fine-tuning is the strongest performance lever in our setup; all three fine-tuned runs are ahead of non-fine-tuned local baselines on lexical metrics.
    \item Prompt engineering is still worth doing before training. Flashcard-style prompting improves quality at almost zero extra cost.
    \item RAG is configuration-sensitive. Retrieval source and top-k both affect quality and latency, and ``more context'' is not automatically better.
    \item Metric triangulation is necessary. ROUGE/BLEU, judge output, latency, and qualitative reading do not always point in the same direction.
    \item This project reaches a reproducible research baseline, not a deployment-ready medical assistant.
\end{enumerate}

\subsection{Limitations}

\subsubsection{Dataset Limitations}

\begin{itemize}
    \item The flashcard format emphasizes concise factual recall, not full clinical reasoning workflows.
    \item Each question has a single reference answer, which can undervalue valid alternative phrasings.
    \item Our report-facing runs use small evaluation subsets for practical compute reasons; this improves iteration speed but increases variance.
    \item Topic coverage reflects the source dataset and may under-represent rare diseases or nuanced guideline-based decisions.
\end{itemize}

\subsubsection{Evaluation Limitations}

\begin{itemize}
    \item ROUGE/BLEU remain lexical metrics and penalize semantically correct paraphrases.
    \item The local judge (\texttt{flan-t5-large}) is useful but not neutral; score-1 concentration indicates limited discriminative granularity.
    \item Semantic adequacy in medicine is inherently context-dependent and can require specialist interpretation.
    \item We did not perform blinded expert annotation, so judge-based conclusions should be considered provisional.
\end{itemize}

\subsubsection{Hallucination Risks}

\begin{itemize}
    \item All model families in this study can generate fluent but incorrect medical statements.
    \item RAG can propagate retrieval errors (irrelevant snippets, outdated medical content).
    \item Fine-tuning improves style/overlap but can also amplify biases in the training corpus.
    \item In a medical context, even low-frequency hallucinations are high-risk; human validation is mandatory.
\end{itemize}

\subsection{Practical Recommendations}

Based on what we observed, this is a practical roadmap for similar projects:

\begin{itemize}
    \item \textbf{Phase 1 (baseline)}: run a local closed-book baseline with two prompt variants before adding complexity.
    \item \textbf{Phase 2 (grounding)}: add one RAG setup and tune top-k conservatively (start with 3, not 5+ by default).
    \item \textbf{Phase 3 (adaptation)}: invest in QLoRA fine-tuning only after baseline instrumentation is stable.
    \item \textbf{Phase 4 (validation)}: combine lexical metrics, semantic judging, and manual review; do not present one metric as definitive.
    \item \textbf{Safety rule}: keep a strict ``education-only'' framing and explicit human oversight requirements.
\end{itemize}

\section{Conclusion}

This project gives an end-to-end comparison of medical QA strategies under realistic student constraints. We did not stop at a single benchmark run: we iterated on the pipeline, completed Colab fine-tuning, and then re-ran evaluation so the final analysis stayed internally consistent.

The main takeaway is practical. Quality is highly sensitive to choices that look minor at first (prompt format, retrieval source, top-k, judge setup, and training data size). In our runs, fine-tuning gives the largest gains, but it does not remove failure modes; prompt and retrieval decisions still matter, and safety risks remain.

\textbf{Main contributions in this report}:
\begin{enumerate}
    \item Reproducible pipeline spanning generation, RAG, fine-tuning, evaluation, and report artifact generation.
    \item Controlled ablations on prompt style, retrieval configuration, and fine-tuning data size (1k/5k/20k).
    \item Multi-angle evaluation: lexical overlap, local semantic judging, latency/format statistics, and qualitative review.
    \item Transparent report of engineering issues and their impact on methodological validity.
\end{enumerate}

\textbf{Next steps}:
\begin{itemize}
    \item Human expert evaluation with adjudication protocol (at least two annotators) on a 30--50 example audit set per main system.
    \item Add a second semantic metric (BERTScore) to reduce dependence on lexical overlap.
    \item Report bootstrap confidence intervals for key metrics (especially ROUGE-L) in all result tables.
    \item Medical-source-constrained retrieval (guidelines/textbooks) with citation tracking.
    \item Better abstention calibration (confidence-aware uncertainty instead of fixed template wording).
    \item Comparative external judging (API judge + local judge) to quantify evaluator bias.
\end{itemize}

This project is for educational purposes only. The generated answers should never be used as medical advice. Healthcare decisions should always involve qualified professionals. We acknowledge the risks of AI hallucinations in medical contexts and emphasize the importance of human oversight.
